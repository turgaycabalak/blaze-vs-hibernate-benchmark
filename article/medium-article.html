Do You Still Need Blaze-Persistence in 2026? I Benchmarked It Against Hibernate 7.4

Four problems Blaze is famous for, tested on 1 million orders. Hibernate now solves most of them. And I found a bug.

Blaze-Persistence is a popular library for JPA and Hibernate. Many teams added it because older Hibernate versions had real problems: slow deep pages, loading lists with their children, building DTOs, and writing advanced SQL like CTEs.

But Hibernate did not stand still. So I asked a simple question: with Hibernate 7.4 and Spring Boot 4.1, is Blaze still worth adding to a project?

This article has two parts. The first part is a short summary. If you only read that, you get the answer. The second part has the details: charts, small code examples and the reasons behind each number.

Part 1: The short version

What I tested

I picked the four jobs Blaze is best known for. For each job I wrote the same query in several ways: with plain Hibernate, with Spring Data JPA, by hand, and with Blaze. Then I measured them on the same database with 1 million orders.

  • Deep pagination: jumping to page 25,000 of a long list.
  • Orders with their lines: “give me the newest 20 orders and all their order lines”.
  • A list screen: building a response with order, customer name and product names.
  • An analytics query: “the latest order of every customer”, which needs a window function and a CTE.

How I tested

  • PostgreSQL 18 in Docker, 100,000 customers, 1 million orders, 3 million order lines. The data is generated the same way every time.
  • Java 25, Spring Boot 4.1.1, Hibernate 7.4.5, Spring Data JPA 4.1.1, Blaze-Persistence 1.6.20.
  • Before timing anything, I checked that every method returns exactly the same data. A fast query that returns wrong data is not a win.
  • Each method ran many times. I report the median time.

What I learned

  1. You don’t need Blaze for fast deep pagination. Blaze was fast. But a small hand-written Hibernate query was just as fast. The surprise: Spring Data’s built-in “keyset” pagination was as slow as normal pagination on PostgreSQL.
  2. Hibernate 7.4 fixed the famous “loads everything into memory” problem. With Hibernate 7.2 (the version in Spring Boot 4.0), the same code needed 3.2 seconds and 1.1 GB of memory for one request. With 7.4 it needs 2 ms.
  3. The real danger in list screens is the N+1 problem, where one request quietly runs hundreds of queries. Spring Data projections fall into this trap too. Blaze avoids it with very little code, but plain Hibernate has good fixes as well.
  4. For CTEs and window functions, plain Hibernate is now better. It was simpler to write and faster to run. And Blaze has a bug here: it silently removed rows from the result (100 rows expected, 8 returned).

So, when should you use Blaze?

  • Use it if you are on Hibernate older than 7.4 (for example Spring Boot 4.0) and you page lists that load child collections.
  • Use it if you have many complex, nested DTOs and you want to write less mapping code. Blaze Entity Views are really pleasant for this.
  • Skip it for keyset pagination, CTEs and window functions. Hibernate 7.4 does these well.
  • Remember the cost: another library to learn, to update and to debug. In this project it also failed to start on a computer with a Turkish locale, and it returned wrong rows for CTE queries.

All code, data and charts are on GitHub, so you can run everything on your own machine: github.com/turgaycabalak/blaze-vs-hibernate-benchmark

Part 2: The details

The test setup

The data model is a small shop: Customer, Product, PurchaseOrder and OrderLine. Every customer has exactly 10 orders, and every order has 1 to 5 lines.

A few rules I followed:

  • Same data for everyone. The data is created with plain arithmetic in a Flyway script, not with random numbers. You get the same rows on your machine.
  • Correctness first. A test checks that every method returns the same result before anything is measured.
  • One request at a time. I measure the cost of one query, not how many requests per second a server can handle.
  • Warm up first. Java gets faster after it runs code a few times, so each method runs many times before I start measuring.
  • The whole call is measured: transaction, SQL and turning rows into Java objects.

Machine: Intel i7-1260P laptop (12 cores), 32 GB RAM, Windows 10, Docker Desktop. The database had enough memory to keep all data in RAM, so we measure the query method, not the disk.

A small lesson: my first run was done while a YouTube video was playing. All numbers were 35–50% higher. The ranking did not change, but I threw that run away. Close your browser when you benchmark.

1. Deep pagination

The problem. The classic way to get page N is OFFSET: “skip N×20 rows, then give me 20”. The database still has to read all the skipped rows. Page 50,000 means reading 1 million rows and throwing them away.

The better way is keyset pagination: “give me 20 rows that come after the last row I saw”. The database can jump straight to that row using the index.

What the numbers say (page 25,000):

  • OFFSET: 251 ms
  • Spring Data keyset (Window) and Hibernate keyset (KeyedPage): about 248 ms. Not faster than OFFSET!
  • Blaze keyset: 1.7 ms
  • Hand-written HQL keyset: 1.4 ms

Why? It is all about how the condition is written. Spring Data and Hibernate generate this:

where created_at < ? or (created_at = ? and id < ?)

PostgreSQL cannot use the index to jump with this condition. It starts at the top and filters rows one by one. At page 25,000 the plan says it removed 499,980 rows.

Blaze writes the same condition as a “row comparison”:

where (created_at, id) < (?, ?)

PostgreSQL uses this directly on the index and reads only 20 rows. The good news: you can write it yourself in HQL.

List<PurchaseOrder> nextPage = em.createQuery("""
        select o from PurchaseOrder o
        where (o.createdAt, o.id) < (:createdAt, :id)
        order by o.createdAt desc, o.id desc""", PurchaseOrder.class)
    .setParameter("createdAt", lastRow.createdAt())
    .setParameter("id", lastRow.id())
    .setMaxResults(20)
    .getResultList();

A trap to know about. Spring Data’s keyset looked fast on the last page (1.7 ms at page 50,000). Why? There are only a few rows left after the last key, so filtering is cheap. If you only test the last page, you will think it works.

Another trap: Blaze counts by default. Blaze’s paginated queries also count all rows, so you can show “page 3 of 50,000”. On 1 million rows this adds about 27 ms to every page, and keyset stops being fast. Turn it off if you don’t need it:

cbf.create(em, PurchaseOrder.class)
    .orderByDesc("createdAt").orderByDesc("id")
    .page(keysetPage, firstResult, 20)
    .withCountQuery(false)   // no COUNT(*) on every page
    .getResultList();

Rule: use keyset pagination for deep lists. Write the row comparison yourself or use Blaze, but don’t assume Spring Data’s Window is fast on PostgreSQL. Test a page in the middle, not only the last one.

2. Orders with their lines

The problem. You want the newest 20 orders and all their lines. The natural code is a join fetch with a limit:

em.createQuery("""
        select o from PurchaseOrder o join fetch o.lines
        where o.createdAt >= :since
        order by o.createdAt desc, o.id desc""", PurchaseOrder.class)
    .setParameter("since", since)
    .setMaxResults(20)
    .getResultList();

For years this was a famous trap. The join returns one row per line, not per order, so Hibernate could not put LIMIT 20 in the SQL. Instead it loaded every matching order with all its lines into memory and kept the first 20. You only see a warning in the log:

HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory

Blaze became famous for fixing this. I ran the same code on Hibernate 7.2 (what Spring Boot 4.0 ships) and on Hibernate 7.4.

What the numbers say (250,000 matching orders):

  • Hibernate 7.2: 3.2 seconds and 1.1 GB of memory for one request of 20 orders.
  • Hibernate 7.4: 2 ms and 0.13 MB. Same code.
  • Blaze: about 3 ms on both versions.

Why? Hibernate 7.4 now picks the 20 orders in a subquery first, and then joins their lines. That is exactly the trick Blaze uses. The problem is simply gone.

A new trap: subselect fetching. Hibernate has a setting that loads collections with a subquery. The subquery has no limit, so it loads the lines of all matching orders: 2.7 seconds and 906 MB at 250,000 orders, even on Hibernate 7.4. Batch fetching is the safer choice. It is one line and needed 2 queries and 2.8 ms:

session.setFetchBatchSize(20);   // or hibernate.default_batch_fetch_size=20

Rule: on Hibernate 7.4 or newer, paging with join fetch is safe, and you don’t need Blaze for this. On older versions, use Blaze, batch fetching, or two queries (ids first, then the rest). Avoid subselect fetching for paged lists.

3. A list screen with nested data

The problem. An API returns a list of orders. Each order has the customer name and a list of lines with product names. The same response was built in seven ways.

What the numbers say (50 orders per page):

  • Loading entities and mapping them to DTOs with getters: 254 queries, about 96 ms.
  • Spring Data interface projection with a nested list: also 254 queries, about 101 ms.
  • The same mapping with batch fetching on: 7 queries, 7 ms.
  • Two hand-written HQL DTO queries: 2 queries, 5 ms.
  • Blaze Entity View: 1 query, 3 ms.

With 1,000 orders per page, the N+1 versions ran 5,001 queries and took about 2 seconds. The hand-written HQL was the fastest there (12.7 ms), and Blaze was close behind (15.9 ms).

Why? This is the N+1 problem. Every getter on a lazy relation can start a new query: one for the customer, one for the lines, one for each product. It is easy to miss, because the code looks innocent. The Spring Data projection surprised me most. It looks like a “projection”, but for a nested list it loads full entities and then does the same N+1.

Blaze solves this with an interface that describes the result. Blaze turns it into one SQL query that selects only these columns:

@EntityView(PurchaseOrder.class)
public interface OrderSummaryView {
    @IdMapping Long getId();
    LocalDateTime getCreatedAt();
    BigDecimal getTotalAmount();

    @Mapping("customer.name")
    String getCustomerName();

    List<LineSummaryView> getLines();   // lines with product names
}

I also tried Blaze’s MULTISET mode, which packs the lines as JSON inside one row per order. Here it was slower than the normal mode (24 ms vs 16 ms at 1,000 orders). It helps when several collections multiply the number of rows. With one small list, it did not help.

Rule: never fill DTOs by calling getters on lazy entities, and be careful with Spring Data projections that contain lists. The cheapest fix is batch fetching. For fewer queries, write DTO queries or use Blaze Entity Views. Blaze wins on less code, not on speed.

4. CTEs and window functions

The problem. “Give me the latest order of every customer.” The modern SQL answer is a window function (row_number()) inside a CTE or a subquery. Old JPA could not do this, and Blaze filled that gap.

Since version 6.2, Hibernate supports CTEs, subqueries in FROM and window functions in HQL:

with latest as (
    select o.customer.id as customerId, o.id as orderId,
           row_number() over (partition by o.customer.id
                              order by o.createdAt desc, o.id desc) as rn
    from PurchaseOrder o
)
select l.customerId, l.orderId
from latest l
where l.rn = 1

In Blaze, the same query needs an extra entity class that describes the CTE columns, plus a builder that binds each column.

What the numbers say:

  • Up to 10,000 customers, HQL and Blaze were close (80 ms vs 110 ms).
  • At 100,000 customers: HQL 884 ms, Blaze 12.5 seconds.
  • A surprise: the old-style JPQL with NOT EXISTS (no window function) was the fastest at 100,000 customers (455 ms), but the slowest for small ranges. Modern SQL is not always faster; it depends on the size.

Why was Blaze so slow? I checked the database first: the SQL plan and database time were the same as HQL (about 1 second). So the time was spent in Java. A quick profile showed that 88% of the time was inside Hibernate’s ListResultsConsumer.addUnique.

For CTE and subquery queries, Blaze asks Hibernate to remove duplicate rows from the result. Hibernate does this by comparing every new row with all rows before it. With 100,000 rows, that is billions of comparisons.

And it gives wrong results. If two rows are equal, one of them is removed. I wrote the same query in HQL and in Blaze, but selected only the customer’s country:

HQL rows:   100  [DE, US, GB, FR, NL, ES, IT, TR, DE, US, ...]
Blaze rows: 8    [DE, US, GB, FR, NL, ES, IT, TR]

No error, no warning. 92 rows are simply gone. This happens with Blaze 1.6.20 on both Hibernate 7.2 and 7.4. A test in the repository documents it.

Rule: on Hibernate 6.2 or newer, write CTEs and window functions in HQL. If you use these Blaze features on Hibernate 7, always select a unique column (like an id), and don’t use them for large results such as reports or exports.

Two more surprises

Blaze did not start on a Turkish computer. Blaze builds some internal names with toLowerCase(). In the Turkish locale, "Integer".toLowerCase() becomes "ınteger" (with a dotless ı), so a lookup fails and Blaze crashes on startup. The fix is to start the JVM with -Duser.language=en. A small thing, but it cost me time.

Versions move at different speeds. Spring Boot 4.1 ships Spring Data 4.1, but Blaze’s integration module is still called spring-data-4.0. It worked in my tests, but every extra library is one more thing to check when you upgrade.

Limitations

These are my results on one laptop, with one database (PostgreSQL), one data model, and one request at a time. Absolute numbers include about 1–2 ms of overhead per call from the transaction and Docker. Look at the shape of the lines, and run the tests on your own setup if the decision matters to you.

Try it yourself

You need JDK 25, Maven and Docker.

git clone https://github.com/turgaycabalak/blaze-vs-hibernate-benchmark
cd blaze-vs-hibernate-benchmark
mvn test                  # correctness tests, about 1 minute
mvn test -Pbenchmark      # all benchmarks, about 45 minutes

Every results folder has the raw numbers, the SQL each method sends, the database plans and the charts.

Final thoughts

Blaze-Persistence solved real problems. But Hibernate 7.4 has caught up on most of them: keyset pagination with a small query, collection paging in SQL, and CTEs and window functions in HQL. What Blaze still gives you is a nice way to write complex DTOs with less code.

So my answer is: don’t add Blaze for performance alone. Add it if its Entity Views save your team real work, and if you accept the cost of one more library.

If you use Blaze or Hibernate in production and see different results, I would love to hear about it in the comments.
